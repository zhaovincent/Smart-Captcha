# 一键人机验证是怎么防住机器人的？（小白版）

> 看完这篇你就明白：为什么"就点一下"的验证码，背后竟然藏了这么多心思。

## 一、先说结论

人机验证看起来只有一步——**用户点一下"我不是机器人"的复选框**。
但点击这个动作本身一分钱不值：脚本（机器人程序）也可以往服务器发一个"我点了"的请求，成本为零。

所以真正的防机器手段**不是点击本身**，而是藏在点击背后的**三道关卡**：

| 关卡 | 防的是什么 | 类比 |
|---|---|---|
| ① 工作量证明（PoW） | 批量刷题的机器人 | 让每个进门的人先搬 100 块砖 |
| ② 随机等待 | 秒回的脚本 | 门卫掐表，而且每个人被要求站够的秒数都不一样 |
| ③ 交互痕迹 | 纯 HTTP 脚本 | 观察你有没有"人味"的动作 |
| ④ 随机界面 | 按固定坐标 / 选择器点按钮的脚本 | 每天换一次门的位置和门牌写法 |

下面一关一关讲。

---

## 二、关卡①：工作量证明——让机器人"搬砖"

这是最核心的一关。

**服务端出题：** 用户打开面板时，服务器随机会发一个"盐"（一串随机字符），并说：
"帮我找一个数字，使得 `SHA-256( SC1|本次题目token|盐|这个数字 )` 的结果**开头 19 个二进制位全是 0**。"

**用人话解释 SHA-256：** 它是一个"搅碎机"——你丢进去任何文字，它都吐出一串 64 位的乱码（十六进制指纹）。特点有两个：

1. **单向**：从乱码倒推不出原文；
2. **雪崩**：原文只改一个字，乱码就面目全非。

**所以找这个数字没有捷径**，只能一个一个试：0 不行试 1，1 不行试 2……平均要试 2¹⁹ ≈ **52 万次**才能碰上开头 19 位都是 0 的"中奖数字"。

**关键的不公平设计：**

- 你的浏览器算这 52 万次，用的是 **Web Worker**（后台小工），面板一打开就悄悄开始算，等用户真点下去时往往已经算完了——**真人无感**；
- 机器人想刷 1 万个验证码？那它得老老实实算 1 万 × 52 万 = **52 亿次哈希**，发一个请求从"零成本"变成了"一段实实在在的电费和 CPU"。

**为什么解不能重复用？** 因为被搅进去的原料里有**本次题目的 token**（每次都不同）。这道题的答案拿到另一道题上验，直接失败——想多刷就得一道一道重新搬砖。

> 类比：银行要求进门的人交一块"特定形状的拼图"。正常人 1 秒拼好（浏览器后台早就拼好了），但黄牛想带 1 万人进来，就得拼 1 万块拼图。

---

## 三、关卡②：随机等待——门卫掐表，而且每次要求不一样

- **每张验证码的要求都不一样**：出题时服务端在 **1~3 秒**里随机抽一个数（比如这张 2.31 秒、下一张 1.5 秒），告诉前端"等够这么久再交卷"，同时把这个数记在本题的答案里；
- 前端点击复选框后真的会等这段时间（界面上表现为"安全校验中"的进度动画），等满才调后端校验；
- 后端做**两道计时**：
  1. 前端上报的"我从看到题到交卷花了多久" ≥ 要求时长；
  2. **服务器自己的表**：从出题到收到校验请求的实际时间 ≥ 要求时长。
- 为什么第二道才是杀手锏？前端上报的数字随便改，但"出题到交卷"的真实时间差是服务器时钟量出来的——脚本拿到题 0.1 秒就提交，无论上报"我等了 99999 秒"都过不去；
- 少传耗时字段？直接判失败。**缺了比不合格更可疑。**

对机器人的效果：每刷一题都要**白等 1~3 秒的随机时间**。想刷 1 万题，光等待就要串行耗掉好几个小时。

---

## 四、关卡③：交互痕迹——你有人味吗？

浏览器会顺手记录这一路的操作（只记数字，不记录你在哪、做了什么）：

- 鼠标**移动**了多少次、划过了多远；
- 有没有**键盘**输入；
- 用的是鼠标、触摸板还是手指。

判定非常宽松：**三种痕迹有任何一种就放行**。
为什么不严格？因为我们已经有关卡①兜底了——能算完 PoW 的"客户端"起码付出了算力成本。这一关只是拦掉最偷懒的脚本：那种不发一个浏览器请求、纯用 curl 模拟的裸 HTTP 机器人，它没有任何交互痕迹，直接出局。

> 诚实说明：这关**防不住**浏览器自动化工具（如无头浏览器），因为它们有完整的鼠标键盘事件。人机验证的定位是"低摩擦的第一道门"，不是保险柜。对改密码、支付这类高危操作，建议失败几次后自动升级成滑块/点选。

---

## 五、通过之后：一次性门票（ticket）

三关都过了，服务端做三件事：

1. **烧掉这道题**（验证码一次性，同一道题验第二次直接拒绝）；
2. **发一张门票**（ticket）：一个 128 位随机字符串，**5 分钟有效**；
3. 你的业务请求（比如登录）带上这张票，业务服务器去验证一下"票是真的、没用过"，就放行。

票是**一次性的**——用一次就作废，捡到别人用过的票也没用。

---

## 六、一图总结

```
用户打开面板
   │
   ├─ 服务端：出题（随机盐 + token + 难度）
   ├─ 浏览器：后台 Worker 悄悄算 52 万次哈希 ←—— 真人无感
   │
用户点一下复选框
   │
   ├─ ① PoW：nonce 对不对？前 19 位真是 0 吗？——服务端一次哈希即可复核
   ├─ ② 等待：够 1~3 秒随机要求了吗？前端上报、服务器自表，两道都得过
   ├─ ③ 痕迹：鼠标/键盘/触摸有任意一种？
   │
   └─ 全过 → 烧题 → 发一次性 ticket（5 分钟）→ 业务接口验票放行
```

**机器人的账：** 刷 1 万题 = 52 亿次哈希 + 真实耗时 + 没有交互痕迹还会被拒。
**真人的账：** 点一下，完了。

这就是"点一下"背后全部的秘密。
